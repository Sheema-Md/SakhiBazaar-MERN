Q1: What is your folder structure?

The codebase is organized as a monorepo consisting of the main marketplace application and a standalone administrative system:

SakhiBazaar_New/
├── backend/                  # Main Express & Node.js REST API Server
│   ├── config/               # Database connection and socket configurations
│   ├── controllers/          # Request handler controllers (Auth, AI, Products, etc.)
│   ├── middleware/           # Auth validation, upload management
│   ├── models/               # MongoDB models & Mongoose schemas
│   ├── routes/               # API endpoint routing declarations
│   └── server.js             # Main server startup entry point
├── frontend/                 # Main Buyer Storefront & Seller Dashboard React App
│   ├── public/               # Static public assets
│   ├── src/
│   │   ├── components/       # Reusable UI components (Navbar, Filters, Cards, etc.)
│   │   ├── context/          # React contexts (Auth, Cart, Language, Theme)
│   │   ├── pages/            # View pages (SellerDashboard, Login, ProductDetails)
│   │   ├── services/         # API connection handlers
│   │   └── main.jsx          # Vite React entry point
│   ├── package.json
│   └── vite.config.js
├── admin/                    # Standalone Administrative Portal
│   ├── backend/              # Standalone Admin Node.js REST API Server
│   │   ├── controllers/      # Admin vetting, product moderation, analytics controllers
│   │   ├── models/           # Shared models (User, Product, Order)

Separation of Concerns: The folder layout isolates client logic (Vite/React 19) from server route logic (Express/Mongoose). Furthermore, the standalone admin portal is completely decoupled with its own backend server and dashboard client, maintaining a separate administrative pipeline that connects directly to the same database.

Q2: How does authentication work?

Authentication in Sakhi Bazaar is built on a stateless JWT validation system combined with password encryption:

  • Email/Password Sign-up: The endpoint POST /api/auth/register validates fields. Phone numbers are restricted to 10 digits and Aadhaar numbers to 12 digits. Passwords must be strong (8+ characters, including at least one uppercase letter, one lowercase letter, one digit, and one special character).
  • Password Hashing: Mongoose middleware pre-save hooks in the User schema automatically hash plaintext passwords using bcryptjs with 10 salt rounds before storage.
  • Authentication and Login: The login endpoint POST /api/auth/login accepts either the email or username as the identifier, matching the input against database indexes and validating the hash using bcryptjs.compare().
  • Google OAuth: POST /api/auth/google-login receives social logins. If the account doesn't exist, it creates a profile in MongoDB using a randomly generated strong password and a customized username.
  • Forgot/Reset Password Flow: The POST /api/auth/forgot-password endpoint generates a 6-digit verification OTP with a 10-minute expiry window, logging it to the console. The user validates the OTP code at POST /api/auth/verify-otp and submits a new password via POST /api/auth/reset-password.
  • Protected Routing Middleware: Upon authentication, a JWT is signed with the user's ID and returned to the client. The client includes the token in the Authorization: Bearer <token> header. The server's protect middleware validates the token, retrieves user details, and stores them on req.user.

Q3: Which JWT flow do you use?

The platform relies on a stateless, token-based Bearer Token Flow handled through HTTP request headers:

  1. Generation: When a user logs in or completes signup, the server signs a JWT containing the user's Mongoose _id in the payload, using a strong signature secret (JWT_SECRET) with a 30-day expiration window.
  2. Storage: The server sends the token in the response payload. The client app intercepts this response and stores the token locally (e.g. in localStorage or inside the React AuthContext state).
  3. Execution: For protected operations, the client appends the token in the standard HTTP header: Authorization: Bearer <token_string>.
  4. Stateless Integrity: The backend does not maintain sessions in database tables or server caches. Instead, it relies entirely on verifying the token signatures on the fly. This architecture ensures high scalability.

Q4: Which APIs have you created?

The codebase runs two backend services. Here are the core endpoints:

A. Main API Router (Port 5000 / Mount: /api)

  • Auth & Preferences (/api/auth): Account CRUD operations, login, registration, Google SSO, language/theme preferences, and OTP-based password resets.
  • Products Catalog (/api/products): List catalog, advanced filtering (categories, subcategories, price range, stock, offers), search query indexing, category stats (min/max/avg), listing CRUD, and product reviews.
  • AI Tools (/api/ai): Description generation and social media captions (integrated with Google Gemini).
  • Market Pricing (/api/market): Commodity market price lists and marketplace category trends.
  • Chat Hub (/api/chat): Send messages and fetch chat history/threads.
  • Transactions & Logistics: Manage shopping carts (/api/cart), place orders (/api/orders), and track courier shipments (/api/shipments).
  • Payments (/api/payments): Stripe checkout integrations, webhook listeners, and transaction refunds.

B. Standalone Admin API Router (Port 5001 / Mount: /api/admin)

  • Auth: Standalone Admin login and registration.
  • Sellers Vetting: List users, review business credentials, and approve/suspend seller statuses.
  • Product Moderation: Review and flag/suspend listings violating guidelines.
  • Platform Analytics: Collect system-wide counts (active users, listings, sales volume, platform commission revenue).

Q5: Which MongoDB collections do you have?

The application models define the following collections in MongoDB:

  • users: User accounts (name, email, password hash, role, status, preferences).
  • products: Catalog listings (title, category, price, images, SKU, stock quantity, creator seller reference, flagging status, and an embedded array of reviews).
  • carts: Shopping cart items, product quantities, and saved-for-later flags.
  • categories: Organizes standard marketplace categories.
  • conversations: Chat thread references between buyers and sellers.
  • messages: Chat logs linked to a conversation thread.
  • notifications: In-app alerts for order updates and portal approvals.
  • orders: Transaction invoices containing lists of items, pricing, and fulfillment state.
  • payments: Logs of payment intents and Stripe confirmations.
  • shipments: Courier delivery logs and tracker data.
  • bookmarks: Bookmarked items.
  • marketprices: Commodity benchmarks (raw craft materials).
  • markettrends: Market indicators and popular products list.

Q6: How exactly does Gemini generate descriptions?

Description generation is handled by the Express aiController using the Google Gemini SDK:

  1. Request Body: The seller submits the product title, category, and optional keywords to the endpoint POST /api/ai/generate-description.
  2. Prompt Assembly: The server builds a marketing copywriting prompt: 
    You are an expert marketing copywriter for 'Sakhi Bazaar', an online marketplace
that empowers women entrepreneurs. Write a highly compelling, professional,
and warm product description for a product with the following details:
- Title: [Product Title]
- Category: [Category]
[Optional Keywords]

Rules:
1. Write in a warm, professional, storytelling style.
2. Keep the description between 80 to 120 words.
3. Return ONLY the plain text description itself. No intro, labels, or markdown.
  3. Fallback and Retry Engine: To avoid rate limits (HTTP 429), the request runs through a retry loop targeting a list of models: ['gemini-2.5-flash', 'gemini-3.5-flash', 'gemini-2.0-flash-lite', 'gemini-2.0-flash']. If a request is rate-limited, the handler backs off exponentially and retries with the next model in the list, returning the trimmed description.

Q7: How does market price analysis work?

Market price analysis works on two layers:

A. Local Platform Price Aggregations

The dashboard queries GET /api/products/stats/category?category=<category> to analyze pricing data based on active listings in that category.

The backend runs a Mongoose aggregation pipeline:

const stats = await Product.aggregate([
  { $match: { category: { $regex: `^${category}$`, $options: 'i' }, status: 'active' } },
  {
    $group: {
      _id: '$category',
      avgPrice: { $avg: '$price' },
      minPrice: { $min: '$price' },
      maxPrice: { $max: '$price' },
      count: { $sum: 1 }
    }
  }
]);

This returns the calculated average, minimum, and maximum prices, helping sellers price new items competitively.

B. Commodity Benchmarks

The endpoints /api/market-prices and /api/market-trends return seeded data for raw materials (such as Pashmina Wool, Mulberry Silk Yarn, Terracotta Clay) to give sellers visibility into regional wholesale prices.

Q8: How is role-based access implemented (Admin/Seller/Buyer)?

Access control is implemented in three layers:

  • Database Schema: The User model defines a role enum (customer, seller, admin) and a status field (approved, pending, suspended). Seller registrations default to pending status, requiring admin approval.
  • Backend Controller Middleware: Express routers use verification middlewares:
    • protect: Parses the JWT and attaches the verified user to req.user.
    • seller: Confirms the user's role is exactly seller.
    • admin: Confirms the user's role is exactly admin.
    These middlewares are chained to guard specific routes: 
    router.post('/', protect, seller, createProduct);
  • Frontend Routing Guards: React dashboards are customized by role (SellerDashboard, CustomerDashboard, AdminDashboard). Frontend routes are wrapped in a ProtectedRoute component that redirects users if their active role doesn't match the route permissions.

Q9: How did you make the application responsive?

The frontend is designed with a mobile-first philosophy using Tailwind CSS (v4):

  • Grid Layouts: Product catalogs use grids that adapt columns based on screen width breakpoints: grid-cols-1 sm:grid-cols-2 md:grid-cols-3 lg:grid-cols-4 gap-6 (1 column on mobile, 4 columns on large monitors).
  • Responsive Flex Layouts: Components stack vertically on mobile and align horizontally on desktop layouts: flex flex-col md:flex-row gap-8.
  • Adaptive Paddings & Constraints: Content sections adjust their padding based on screen size (e.g. px-4 sm:px-6 lg:px-8), and elements scale with fluid widths (e.g. w-full md:w-1/2) to prevent layout breakages.
  • Conditional Visibility: Utility classes like hidden sm:flex or hidden lg:block hide elements on smaller screens to keep mobile views clean.

Q10: How would you deploy it?

The application is designed for cloud-based deployment, separating static assets, backend APIs, and database hosting:

  • Frontend SPA: Compile static assets via npm run build in the frontend folder. Host the compiled assets on CDN-backed static hosting platforms like Vercel, Netlify, or AWS S3 + CloudFront. Configure routing to redirect all subroutes to index.html to support React Router client-side routing.
  • Backend Server: Deploy the backend REST server to cloud application hosts like Render, Railway, AWS Elastic Beanstalk, or containerized within **Google Cloud Run**. Use PM2 on virtual machines for process monitoring, memory management, and automatic crash restarts.
  • Database Hosting: Host database instances on MongoDB Atlas (managed database-as-a-service), using IP whitelisting to restrict access only to the backend server's IP address.
  • Media & Cloud Services: Upload product images to Cloudinary (configured via backend middleware) to optimize images and serve them through their global CDN. Use production Google AI Studio keys for Gemini API requests.
  • Environment Secrets and CI/CD: Store sensitive credentials (MONGO_URI, JWT_SECRET, GEMINI_API_KEY, etc.) securely as environment variables on the hosting platform. Set up a CI/CD pipeline using GitHub Actions to automate testing and deployment on push to the main branch.
